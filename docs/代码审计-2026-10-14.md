## P1：优先修复

### 01. 删除章节会同时删除下一章的批注

位置：`app/src/main/java/com/inkreader/data/repo/BookRepository.kt:1066`，关联 `InkDb.kt:449`。

代码先把后续章的批注编号减一，再按被删章的旧编号删除批注。因此原下一章的批注已迁入这个编号，会被一起删除。例：删除编号 0 的章节，原编号 1 的高亮、笔记、书签全部被误删。事务只保证这些错误操作一起提交，不能防止误删。

验证：内存 SQLite 复现中，原章 0 和章 1 的两条记录都被删掉，只剩原章 2 的记录。

修复：先删目标章批注，再移动后续章编号；补覆盖目标章、下一章和更后章节的仓库级回归测试。

### 02. 拆章在进入恢复保护之前覆盖原文，写新文件失败会丢后半章

位置：`BookRepository.kt:801`。

`files.write(curr.fileName, firstText)` 已经把原章覆盖为前半章，随后新章正文写入才发生；恢复逻辑的 `try` 从 809 行数据库事务开始。如果新章写入因磁盘空间不足等原因失败，根本不会执行恢复。数据库仍指向原章文件，但文件只剩前半章。原文件写入本身也是直接截断覆盖，写到中途失败同样没有保护。

修复：在覆盖之前进入完整异常保护，采用新文件暂存、原子替换和可恢复的提交流程；失败时恢复正文与 `.rich`，不要只保护 SQL。

### 03. 文件读取失败被当成空正文，合并/重分章可永久删除未读到的内容

位置：`app/src/main/java/com/inkreader/data/file/FileStore.kt:42`；调用 `BookRepository.kt:691`、884。

`read` 捕获所有读取异常并返回空串。合并时如果本章暂时读取失败，会按空章合并后删除本章记录和正文文件；重分章中只要还有其他可读章节，就会拿不完整全文替换所有旧章并清理旧文件。读取错误因此升级为内容丢失，而且用户不会收到读取失败提示。

修复：区分真实空正文与读取失败。所有破坏性操作必须要求每个输入章节读取成功，否则中止并保留原数据。

### 04. 编辑器系统返回不保存，顶部返回也不等待保存完成

位置：`app/src/main/java/com/inkreader/ui/editor/EditorScreen.kt:107`、134；`MainActivity.kt:372`。

自动保存延迟 1.2 秒。系统返回由根路由直接 `pop()`，编辑器没有自己的 BackHandler，刚输入的内容会随着页面退出和自动保存协程取消而丢失。顶部返回先在页面作用域启动保存，立即退出；保存没有完成屏障，页面移除后协程可能在文件写入前或标题更新前取消。转场的 300 毫秒不能替代保存完成保证。

修复：统一退出路径，等待保存成功后导航；失败留在编辑页并提示。避免自动保存、手动保存和拆章同时改写同一文件。

### 05. 听书预排队列没有续补，超过三句的章节会停住

位置：`app/src/main/java/com/inkreader/tts/TtsService.kt:204`、320。

`speakCurrent` 只提交当前句及后两句，`PREFETCH=2`。`onDone` 对未到章末的情况只增加 `sentencePos` 并发布状态，没有提交下一句或补队列。读完这三句后，剩余正文没有任何播放任务；状态和通知却仍显示播放中。从章节中间启动也只读最多三句。

验证：检查全部 `engine.speak` 调用及全部 `speakCurrent` 调用，普通句结束路径无任何续补。

修复：记录已排队句子的边界，每完成一句补入下一句；处理引擎提交失败，补至少四句章节的队列测试。

### 06. 合并换行的正文块使用原文起点和压缩后长度，渲染会漏字并使批注错位

位置：`app/src/main/java/com/inkreader/ui/reader/Paginator.kt:355`、386；`ReaderScreen.kt:1590`。

空行比例较高时，`toBlocks` 把同一段内的多行拼起来，删除换行及行首空格，中文之间不加分隔。Block 保留原文起点，而分页的结束位置按拼接后长度计算。渲染端又从未压缩的原文 substring，两个坐标系不一致。

验证：原文 `甲乙\n丙丁\n\n尾段\n\n末段`，第一块文本为 `甲乙丙丁`，按实际页坐标截原文却得到 `甲乙\n丙`，`丁` 被漏掉。长按选区、页码进度与批注偏移也会随之错位。

修复：块始终保留原文连续区间，或提供完整的显示字符到原文字符映射；测量、渲染、选择和标记必须使用一致的坐标。

## P2：功能与健壮性问题

### 07. 重分章的批注回退坐标不处于同一基准，重复片段也会迁移到错误章节

位置：`BookRepository.kt:882`、923、963、980。

旧全局起点包括补入的章节标题和归一化后的段落，但直接加的是未归一化正文的旧偏移；新章区间则用重分章后去掉标题的正文长度从零累加。删除标题、水印、空白后这套累计区间不再对应原全文。无 snippet 的书签容易漂移。snippet 有值时只找全书第一处相同的前 24 字，重复对白会被迁到更早章节，不能保证无损。

修复：切分与清洗阶段保留源文本区间映射，按旧锚点找新位置；片段搜索限定在预计位置附近并处理重复命中。

### 08. UTF-16 被格式识别拒绝，无 BOM 的大小端推断也写反了

位置：`app/src/main/java/com/inkreader/parse/DocumentFormat.kt:75`、118；`CharsetDetector.kt:41`。

FormatDetector 在解码之前把前 4096 字节含 NUL 的输入判为二进制。UTF-16 常包含 NUL，即使有有效 BOM 和 `.txt` 扩展名也返回 UNKNOWN。另一个独立错误是：ASCII 文本 UTF-16LE 的零字节集中在奇数位，代码却推断为 BE；BE 反过来也被推成 LE。

验证：实际源码对带 BOM 的 LE/BE 样本均返回 UNKNOWN，直接解码能正确还原。无 BOM 的英文 LE/BE 样本被推断成相反编码且解码错误。

修复：先识别 BOM/UTF-16，再检查文本有效性；修正奇偶位判断，并覆盖大小端、有无 BOM、中文和英文样本。

### 09. 缓存文件名前置时间戳破坏章号与书名识别

位置：`app/src/main/java/com/inkreader/ui/component/PickerIntents.kt:85`；重复实现 `MainActivity.kt:297`。

缓存路径采用 `时间戳_原文件名`，但后续 displayName(file URI) 直接返回完整文件名，原始名称没有单独保留。区间规则要求区间前缀不含数字，时间戳使它失配，并退回取尾部数字。文件名生成的书名/章名还会带上时间戳。

验证：`5-7.txt` 章号为 5，加时间戳后实际返回 7。该路径由书架选择器实际调用，并非仅存在于旧代码。

修复：唯一目录下保留原始文件名，或把 URI 与原始显示名称作为独立元数据传递；统一两份缓存实现。

### 10. 选择器回调在主线程无界复制文件，80MB 上限只信声明大小

位置：`PickerIntents.kt:65`、87；`ShelfScreen.kt:199`。

授权获取失败时回调直接执行文件复制，云端文件、慢存储、多文件会阻塞界面。大小未知（-1）或声明大小不准确时，`input.copyTo` 不检查实际字节数，80MB 限制不起作用；导入阶段的 200MB 检查发生在复制结束之后。失败的半成品缓存也没有即时清理。

修复：只同步获取授权；复制放到后台，流式计数、超限中止、删除临时文件，再发布导入结果。

### 11. 正文区小于一行高度时，分页器会无限循环

位置：`Paginator.kt:302`。

`avail < lineHeightPx` 时 flush 并 continue。空页 flush 不增加页数，used 重置为 0，cursor 不前进。如果整页高度仍小于该块的一行高度，这个条件永远成立。多窗口、小正文区域、系统字体放大或 Markdown 大标题可触发；当前章节排版在主线程执行，会卡住界面。

修复：空页也放不下一行时必须有推进/拒绝策略；页尺寸、字号极值验证应覆盖这一情况。

### 12. 全书页数计算没给章首页标题留高度

位置：`ReaderSession.kt:191`，对照 339、448。

实际分页和邻章分页都传 `firstPageInsetPx`，全书计数却使用默认 0。接近一页边界的章节，计数可能是一页，实际是两页；全书总页数偏小、后续章节累计页码错误，违背“真实页码”的核心功能。

修复：计数与正文分页复用同一参数构造函数，包括标题高度和所有影响布局的参数。

### 13. Markdown 行内样式参与绘制但不参与分页测量

位置：`Paginator.kt:309`、315；`ReaderScreen.kt:1899`。

分页器测量纯 String 和块级 TextStyle；渲染端额外给行内代码套 Monospace，并给粗体/斜体套 SpanStyle。这些样式可能改变文字宽度、换行和高度。特别是普通段落中较长的行内代码，实际绘制可能超过已分配页面高度。

修复：测量与绘制复用同一 AnnotatedString；验证行内代码、粗体、跨页文本和混合字体。

### 14. 指定章节且偏移为零时，读取了上次章节的偏移

位置：`ReaderSession.kt:243`。

`initialChapter >= 0` 但 `initialOffset == 0` 时仍用 `b.lastCharOffset`。从章节列表点开某章，或从偏移零的标记跳转，会从旧章的历史偏移开始，甚至直接落在新章末页。

修复：只要明确指定章节，就使用传入偏移（包括零）；仅在未指定章节时恢复历史位置。

### 15. 切章请求与邻章预加载缺少代次校验，可覆盖更新后的阅读状态

位置：`ReaderSession.kt:263`、393、409。

每次加载都另起协程且未取消旧请求。连续选 A、B 章时，若 A 的读取更晚完成，就会覆盖已经显示的 B。邻章缓存只校验相邻章编号，不校验字号/尺寸/正文版本；排版变化清掉缓存后，旧预加载仍可回来重新放入旧排版结果。

修复：加载任务取消加请求代次校验；缓存键包含章节身份、正文版本及排版参数，并在每次发布前检查。

### 16. TTS 停止后仍有加载协程与旧回调，切书会混用状态

位置：`TtsService.kt:156`、174、292、314、553。

服务 scope 没有在销毁时取消；stopEverything 只停引擎、计时任务和通知。正在读取正文的协程稍后仍能发布 active=true。开始新书未取消旧加载和旧队列，utteranceId 只有句子编号，无书籍/章节/播放代次；旧句回调可能改变新章节的 sentencePos 和进度。

修复：可取消的加载任务、播放代次 ID、切书清队列；停止后禁止旧任务发布状态，销毁时取消作用域并妥善完成最后进度保存。

### 17. 听书定时停止在每次切章时重新计时

位置：`TtsService.kt:198`、376。

每次 loadChapter 调用 applySleepTimer，后者取消旧计时并把结束时间设置为“现在 + 指定分钟”。用户选 15 分钟，只要 15 分钟内又切章，倒计时就重置；连续短章可能一直不会按原计划停止。

修复：选择定时时确定截止时间，跨章保持截止时间；只有用户更改定时或开始新的播放会话时重置。

### 18. 导入/追加缺少完整提交与失败清理，失败仍留下半本书

位置：`BookRepository.kt:153`、483、492、593、625。

单文件导入先插入书并加入成功 ID 列表，再逐章写文件、插入数据库，没有包裹完整事务和补偿。中途异常被外层记作导入失败，却留下书记录和已写章节，统计可能仍为零。合并导入的写盘异常会直接中断全流程。追加的 idx 在插入时先增加，插入返回 -1 未清理文件，也可能留下编号缺口。insertBook 返回 -1 也没有统一检查。

修复：按每本书/每个输入文件定义提交边界，暂存正文，所有插入结果严格检查；失败清理暂存数据并让结果列表反映实际提交状态。

### 19. 听书通知携带打开书籍参数，但应用入口完全没有消费

位置：`TtsService.kt:473`；`MainActivity.kt:329`、358。

通知 PendingIntent 写入 EXTRA_OPEN_BOOK，MainActivity 的创建/新 Intent 处理仅处理 VIEW/SEND，InkRoot 也没有读取此参数。应用冷启动时点通知只到书架，已有页面时也不会按这本书导航。

验证：全项目搜索 EXTRA_OPEN_BOOK，仅找到写入和常量声明，没有读取。

修复：将通知打开请求投递到统一导航状态，定位对应书籍与当前朗读位置，并在消费后清除。

### 20. 拆章去掉空白后可能生成 endOffset 小于 startOffset 的标记

位置：`app/src/main/java/com/inkreader/data/repo/MarkShifts.kt:68`。

拆点在原章尾部空白之后时，firstText.trimEnd 会缩短前半章。位于这段被移除空白里的标记仍留在原章；当前分支只把 endOffset 改成 firstTextLength，没有限制 startOffset。书签尤其容易变成非法范围。

验证：拆点 10、前半章裁剪后长度 6、书签位于 8，实际源码返回 start=8、end=6。

修复：同时约束起止点，并明确被删除文本内的标记迁移策略；不只截断终点。

### 21. Markdown 重分章会把已经渲染的纯文本再次当 Markdown 解释

位置：`BookRepository.kt:884`、927；`RichMarkdown.kt:62`。

首次导入已把 Markdown 转成纯文本与 `.rich`。重分章只读纯文本，没有恢复原始 Markdown或迁移样式，随后按 book.sourceType=MD 再次 prepareBody/render：原有粗体、链接、代码块等样式丢失；代码块中原本作为字面量显示的 `**文字**` 等还可能第二次被当语法处理并改变正文内容。Markdown 书中追加其他格式的纯文本章节也会被同样重新解释。

修复：重分章面向当前正文和样式区间迁移；避免用书级 sourceType 猜测章节正文仍是原始 Markdown。

## 其他观察与验证边界

- `backup_rules.xml` 和 `data_extraction_rules.xml` 包含 chapters，但没包含 covers，换机恢复后数据库仍有 cover_path，自定义封面文件却未恢复。`FileStore.writeCover`/writeRich 还吞写入异常，界面可能报告成功而文件没有更新。
- 清单允许系统备份，规则明确允许 cloud-backup 中包含书籍与笔记。README“只在本地、不上传”应说明应用不主动联网与系统备份的边界，或调整备份配置；这里没有证明发生过任何实际上传。
- ZIP 条目大小限制主要限制保留的数据；跳过条目仍 closeEntry，需要检查极高解压比输入的 CPU/耗时预算。EPUB 对损坏条目和超限正文有静默跳过路径，应避免把不完整书报告成完整导入。本次没有进行压力测试。
- 重分章 2000 万字符上限在拼完整书并 toString 后才检查，对拼接阶段的内存峰值无保护；应逐章累计并提前拒绝。
- 暂未发现需要报告为已证实漏洞的任意 SQL 拼接注入或联网传输；不能据此宣布安全审计“无漏洞”。
- 没有 SDK/模拟器/真机，未验证国产 ROM 文件选择器、系统 TTS 引擎、旋转与进程重建、低存储异常、实际字体测量和权限行为。依赖漏洞与发布签名未做外部数据库检查，本报告也不包含发布合规结论。

## 修复与回归顺序

1. 删章批注顺序、编辑退出保存、拆章文件提交、破坏性读取失败保护。
2. TTS 队列续补和播放代次；正文块坐标一致性。
