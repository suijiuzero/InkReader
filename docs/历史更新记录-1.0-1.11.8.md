# 历史更新记录（1.0–1.11.8）

以下保留旧版本当时的变更说明，不能作为当前操作、验证范围或签名行为的依据。当前手册见 [使用说明](使用说明.md)，后续版本见 [CHANGELOG](../CHANGELOG.md)。

## 更新日志

### v1.11.8（本次：修「第一次导入必然失败」+ 选择器改用 AOSP）

**一、「第一次导入失败、第二次才成功」—— 根因找到了（vivo 真机留痕为证）**

| 尝试 | 过程 | 结果 |
|---|---|---|
| 第 1 次 | 点导入 → **vivo 隐私密码 / 指纹页** → 文件管理器 → 选文件 → 完成 | 4.93 秒后 `res=0 uris=0 data=false` ❌ |
| 第 2 次 | 点导入 →（不再弹验证页）→ 文件管理器 → 选文件 → 完成 | 2.39 秒后 `res=-1 uris=1 data=true` ✅ |

vivo 的**隐私密码 / 指纹验证页属于另一个任务栈**，平台会把这次"选文件"的结果直接判成"取消" ✗；
指纹只要验证过一次就不再弹，所以表现为"第一次必失败、第二次才成功"。

**修法**：选文件**明确指定 AOSP 的 `com.android.documentsui`**（它没有这个验证环节），
同时改用契约托管的回调（跨任务、Activity 重建都能把结果接住）。找不到该组件时自动退回系统默认解析。

**二、其它**

- 选择器意图与系统标准契约对齐（不再传二十多个具体 MIME 的过滤列表）——
  实测部分 ROM 的选择器面对长过滤列表会直接返回空结果。
- 结果回来时若拿不到持久授权，就把文件**抄一份进应用私有缓存**（保留原文件名，章标题与按章号排序要用它），
  彻底避免"选好了文件、点开始导入却报读取失败"。
- 移除排查期间加入的临时前台服务与两条多余权限声明（实测证明它们针对的方向是错的）。

### v1.11.2（区间文件名排序取「区间起点」）

一本书拆成几个文件、名字写成**章号区间**是很常见的做法，比如：

```
诡秘之主1-4.txt      5-7.txt      8-11.txt
```

**之前的问题**：区间必须在名字**开头**才认。第一个文件名前面有书名（`诡秘之主`），区间规则匹配不上，
于是落到「结尾数字」规则，把 `诡秘之主1-4` 解析成 **4**（区间末尾）而不是 **1**（区间起点）。
`4 < 5` 只是碰巧排对；一旦区间跨度重叠（`1-9` 与 `10-12`）或者前缀变了，顺序就乱。

**现在**：区间规则允许前面有一段**不含数字的前缀**（书名），并且**始终取区间起点**；分隔符支持
`-`、`–`、`—`、`～`、全角破折号，以及中文「到 / 至」。

| 文件名 | 序号 |
|---|---|
| `诡秘之主1-4.txt` | **1** |
| `5-7.txt` | 5 |
| `8-11.txt` | 8 |
| `诡秘之主5-7.txt` | 5 |
| `诡秘之主１－４.txt`（全角） | 1 |
| `诡秘之主9~12.txt` | 9 |
| `诡秘之主1到4.txt` / `7至9.txt` | 1 / 7 |
| `第3-6章 风起.txt` | 3（`第X章` 优先） |

于是上面三个文件合并为一本书时，顺序是 **`1-4` → `5-7` → `8-11`**；文件内部若本来就有
「第X章」标题，合并后还会再按章号把整本排一遍（见 v1.10.3）。

### v1.11.1（本次：文件名序号识别 + 首次导入的最后两处残留）

**一、文件名尾部的序号现在认了**

有些书是一本拆成多个文件、命名像 `你好1.txt`、`你好2.txt`、`你好3.txt`。以前这种**解析不出章号**，于是：

- 文件之间的先后只能听系统文件选择器给的顺序（并不可靠）；
- 合并导入时被当成「没编号的文件」，退回按**文件内部**标题分章 —— 而每个文件里只有「第1节」，
  于是切出来**全叫「第1节」**。

现在认**结尾的阿拉伯 / 全角数字**（`你好3`、`Part12`、`你好５`）。优先级没变：

| 文件名 | 解析出的序号 |
|---|---|
| `第9章 决战2024.txt` | 9（`第X章` 优先，不被尾部数字带跑） |
| `你好1.txt` / `你好2.txt` / `你好12.txt` | 1 / 2 / 12 |
| `你好５.txt`（全角） | 5 |
| `第一部3.txt` | 1（卷级标记「第一部」优先） |
| `前言.txt` | -1（前置内容，排第一章之前） |
| `杂记.txt` | 无（保持原顺序排最后） |

**二、首次导入仍可能失败的最后两处**

1. **不再「固定延时之后就判定选择器被打断」**：系统派发结果的时机不确定，可能晚于任何固定延时；
   一旦先判成「被打断」并重开选择器，刚选好的结果就被冲掉了。现在改成 2.5 秒宽限期内轮询 ——
   结果一到就用结果，等满仍没有才重开。
2. **拿到 Uri 的那一刻就落实「以后一定读得到」**：先试持久化授权并真读一次；拿不到授权或读不到，
   就把内容抄一份进应用私有缓存（**保留原文件名**，因为章标题和按章号排序都要用它）换成 `file://`。
   解决的是「进程被 ROM 冻结/杀掉重建后，临时 Uri 授权失效 → 点开始导入报读取失败，再试一次又好了」。

### v1.10.10（本次：导入与解析健壮性加固）

这一版没有新增可感知的功能，主要是把几处「极端输入下会出问题」的地方收口，日常使用没有变化：

- **超大文件不再拖垮 App**：导入单个文件超过 200MB 时直接给出「文件过大」提示，而不是先整个读进内存导致卡死或崩溃；DOCX / EPUB 解压时对压缩包内的单个条目也加了体积上限，避免畸形压缩包撑爆内存。
- **删除更可靠**：删书、删章的多步数据库操作改为一个事务，中途出错整体回滚，不会留下「书没了、章节还挂着」这类残缺数据；删除正文文件失败也不影响删除本身完成。
- **发布签名可切换**：在工程根目录放 `keystore.properties` 即可使用正式签名打包；不提供时仍回退调试签名，行为与之前一致。

> 老版本的用户数据没有任何变化，升级即可用。

### v1.10.8（翻页动画新增「覆盖」与「仿真」，翻页改为整屏）

「翻页动画」现在有四档，顺序是 **平移 / 覆盖 / 仿真 / 无动画**：

| 档位 | 效果 |
|---|---|
| 平移 | 两页一起滑动（原来的效果） |
| **覆盖** | 下一页先完整铺在底层不动，当前页在上层像被抽走一样整体平移出去，逐渐露出新页；不做变形、不加折痕与重阴影，干净、快 |
| **仿真** | 当前页像纸一样被折过去，露出下一页；折过去的纸背**能透出旧页的字**（镜像文字压一层纸色），折线上有高光、折痕旁有投影 |
| 无动画 | 立刻切换，不做缓动 |

**覆盖 / 仿真的操作方式**：左右拖动跟手（覆盖=旧页跟着手指移走，仿真=折线跟着手指走；拖动不足半页回弹，够了就翻过去；快速甩动按速度决定），点击屏幕左右边缘也能翻。到达书首/书末或正文还没排好时会自动不响应，不会出现空白页。

**翻页改成了「整屏」**：页眉（返回 + 章节名）和页脚（页码 / 百分比）现在是**每一页自己带着走的**，翻页时跟着整页一起动，而不是正文在页眉页脚之间挪动 —— 四档都是这样。文字位置、分页结果、页码统计和以前完全一致（页眉页脚占的位置在排版时照样留白）。

**实现上的两点取舍**（写在这里免得以后误会）：

- 仿真是**二维折页**：折线是竖直的，纸背只做镜像正文 + 纸色压暗，**不是三维卷曲**，也没有纸张弯曲的弧度。要升级成三维只改折页几何那一处，其它调用点不用动。
- 覆盖与仿真都**不走横向分页器**（旧版删掉的那两种就是因为画在了分页器里、绘制顺序压不住旧页才被判不值）。现在这两档有自己的一层绘制，绘制顺序自己控，所以「旧页压在新页上面」这件事才做得成。两者共用同一套叠层、手势与页码提交，只有「旧页怎么离开」不同。

> 升级提示：很老的版本存过「卷曲（CURL）」设置，这个值在新版里没有对应项，会自动落回「平移」，需要到「设置 → 翻页动画」里重新选一次；「覆盖」这个名字沿用旧名，老设置能直接对上。

### v1.10.7（本次：新增 Markdown / PDF / HTML / EPUB 导入，章节识别支持英语 / 日语）

**从「只能读 TXT 和 docx」扩到六种格式**，同时把解析这件事收拢成一套统一的管线。

| 新增格式 | 怎么解析 |
|---|---|
| `.md` / `.markdown` | 按 `#` 标题层级分章；**保留 Markdown 排版**（标题、粗体、斜体、删除线、行内代码、列表、引用、代码块、表格、链接、任务列表），YAML 头信息里的 `title` / `author` 用作书名作者 |
| `.pdf` | 用 **pdfbox-android** 提取文字（系统自带 API 只能把页面画成位图，拿不到文字）；按页面边界组织阅读顺序，按字号识别标题，每页重复的页眉页脚自动剔除 |
| `.html` / `.htm` | 提取 `<title>` 与正文，丢掉 `script` / `style` 等无关内容，`h1~h6` 转成章节层级 |
| `.epub` | 解析容器与 OPF，**按 spine（阅读顺序）逐章**提取 XHTML 正文 |

**三件配套的事**：

1. **统一解析架构**：格式识别（文件头魔数 + 内容嗅探）与解析器解耦，导入链路只调一个入口。原有的 TXT / docx 解析逻辑一行没动，只是套了层适配壳 —— 老格式的导入行为完全不变。
2. **错误提示统一管理**：所有解析器共用同一套文案。导入 `.zip` / `.xls` / `.ppt` 这类不支持的文件，会明确说「**暂不支持该文件格式（ZIP 压缩包）**」，而不是笼统的「导入失败」；`.doc` 会提示先另存为 `.docx`；文件损坏、内容为空、PDF 加密、疑似扫描件各有各的说明。
3. **批量导入结果明细**：一次导入多个文件时，只要有失败项，就弹一张明细表 —— **哪些成功（各几章）、哪些失败、失败原因**逐条列清楚。

> 代价：PDF 解析引入了 pdfbox-android（纯 Java，无 so、无 AWT），安装包会增加约 4~5MB；Markdown 解析引入了 commonmark-java（纯 Java，无 so、无 Android 依赖，约 300KB），体积影响可忽略。

**Markdown 现在是「格式化阅读」而不是「去标记」**（新增）：

以前导入 `.md` 是把粗体、反引号这些标记直接删掉，只留纯文本。现在改成**保留排版**：

| 类别 | 支持内容 |
|---|---|
| 标题 | H1–H6，字号逐级递减、加粗，前后留白更大 |
| 行内 | **粗体**、*斜体*、~~删除线~~、`行内代码`（等宽 + 淡底色） |
| 块 | 段落间距、连续空行压缩、`---` 分隔线 |
| 列表 | 有序 / 无序 / 嵌套列表，项目符号与序号画在左侧留白里 |
| 引用 | 引用块与嵌套引用，左侧一条竖线 |
| 代码块 | 围栏与缩进式代码块，保留缩进与换行，等宽字体 + 淡底 |
| 表格 | 保留行列结构，等宽对齐；过宽时自动换行而不是挤成一团 |
| 链接 | `http` / `https` / `mailto` 链接着色可点，点按用系统打开；其它协议退化成普通文字 |
| 任务列表 | `- [x]` / `- [ ]` 显示成 ☑ / ☐ |
| 图片 | 正文里显示为「［图片：替代文字］」占位（不联网加载） |

排版**跟随阅读器的字体、字号、行距、主题和背景设置**；标题层级照旧参与分章与目录跳转；格式化内容正常参与分页、翻页与阅读进度记录。

> 关键点：格式不只在导入时保留，**也贯穿分页**。一段加粗文字跨到下一页时两页都保持加粗，代码块被切开也不会丢缩进 —— 分页引擎按「块」来量高度和缩进，渲染端用同一套规则绘制。
>
> 实现方式：正文仍然是纯文本（朗读、搜索、选区、进度全都按字符偏移工作，一个字没改），格式化信息作为「样式覆盖」另存一份，两者偏移严格对齐；对不上时自动退回纯文本阅读，绝不会因为样式坏了导致整本书打不开。

### v1.10.6（本次：正文里提到「第X章」不再被误判成章节标题）

**问题**：如果正文里出现「一本书的第一章」这类**引用**，会不会被当成分章标题、把一章切碎？

**先说结论：绝大多数情况不会**，因为识别标题本来就有 4 道关卡：

1. 标题模式要求**整行匹配**（`^第X章 …$`）—— 正文里「…那本书的第一章…」这种行，**行首不是「第X章」**，直接不匹配；
2. 标题行**长度 ≤ 44 字**（正文句子通常更长）；
3. 标题行**不以句末标点结尾**（。！？…"）—— 正文句子几乎都带；
4. 要求**独占一行**（前后有空行，或下一行明显是长正文）；
5. 还要够 **≥2 个**强标题才会走「按章拆分」，否则退回按字数切。

**仍会漏的一种**：一行**以「第X章」开头、又不带句号**的正文，例如独立成行的

```
第一章里提到的那个名字
```

这种会被误当成标题。v1.10.6 补了第 6 道关卡：**看「第X章」紧跟着的那个字** —— 跟着「的 / 里 / 中 / 是 / 有 / 说 / 在 / 和 …」这类连接词，就判定为**正文在引用某一章**，不算标题。

| 行 | 结果 |
|---|---|
| `第一章 初见`、`第12章 破境`、`第十二章`、`第一卷 风起` | ✅ 标题（正常拆章） |
| `第一章里提到的那个名字`、`第三章的约定` | ❌ 判为引用，不拆 |
| `他翻开了那本书的第一章` | ❌ 行首不是「第X章」，本来就不匹配 |
| `第一章 的约定` | ❌ 判为引用（真标题不会以「的」开头） |

（这 10 个用例我都在本地按同一套正则跑过，结果与预期一致。）

### v1.10.5（单个文件导入也自动按章号排序）

**你问的那个情况：只导入一个文件、但文件里的章节是乱的 —— 之前不会自动排。**

原因：自动排序只接在「**合并导入（多文件）**」那条路径上；**单个文件**走的是另一条路（`各自成为一本书` → 解析文件内章节），解析出来是什么顺序就按什么顺序建章，乱序就一直是乱序。

现在：**每个导入的（每本）书都会在导入结束时按章号排一遍**，包括：

- 单个文件导入；
- 多文件「各自成为一本书」（每本各自排）；
- 多文件「合并为一本书」（这个 v1.10.3 已经有了）。

安全性：排序前会先比较，**顺序没变就完全不写库**，所以正常的书导入后不会有任何变化；只有真的乱序（章号能解析出来、但排列不对）才会被纠正。

另外，单文件导入的对话框里现在会明说这一点：「会自动识别文件里的「第X章」标题拆成章节，并按章号排序 —— 文件内部章节顺序乱掉也能纠正过来。」

> 提醒：排序依赖**章节标题能解析出章号**（`第12章`、`第十二章`、`Chapter 12`、`Chapter One`、`第12話`、`003 xxx`、`28` 这些写法都认）。如果标题里没有任何编号，那就无从判断先后，只能保持原顺序 —— 这种情况请用章节管理的「上移 / 下移」手动调。

### v1.10.4（修「章节管理里删掉整本后一直转圈」）

**现象**：从阅读器进章节管理删掉整本书 → 页面转圈圈，但其实书已经删了；手动手势退到书架就一切正常。

**原因**：删除成功后我只做了「**返回上一级**」，而上一级正是**那本刚被删掉的书**的阅读器 —— 阅读器加载不到书，就一直停在 loading 转圈。

**修法（两道保险）**：

1. 删除整本书后**直接回书架**（一路弹到底），不再落回那本已经不存在的书；
2. 阅读器自己也加了兜底：**加载完成但书不存在**时不再转圈，而是显示「**这本书已经被删除了**」+ 一个「返回书架」按钮 —— 这样不管从哪条路径把书删掉，都不会再出现死转圈。

### v1.10.3（智能解析合并后自动按章号排序）

v1.10.1/1.10.2 只做了「**文件之间**按文件名章号排序」，而 **文件内部拆出来的章节顺序、以及"单章文件"和"合集"交错的边界**并没有保证 —— 你要的「智能解析自带排序」缺的就是这一步。

现在：**合并导入时选了「智能解析」，成书后会再按章号把整本排一遍**（走的就是章节管理里那个「自动排序章节」的同一套逻辑）：

- 合集文件内部拆出来的 1~9 章、和单独文件带来的第10章，最终一定按 1→2→…→10 排好，不管文件是哪种顺序选进来的；
- 前置内容（序、楔子…）在最前，后记/番外/解析不出章号的在后（保持相对顺序）；
- 顺序本来就没变的话不写库，不会白折腾。

> 「追加文件为章节」不走这一步 —— 追加时是**按章号插到对应位置**（只动新加的，不打乱你手动调过的顺序），两者行为不同是有意的。

### v1.10.2（修智能解析把「节」当章拆 + 修对话框按钮被挤出屏幕）

**一、智能解析：不再把「第X节」当章来拆**

v1.10.1 的判据是「分片标题里的章号有两个以上不同的值就拆」，而解析器**把「第X节」也当章节标题**，于是一个「第10章」里含三节的文件被拆成了 **3 章** —— 你要的是**一整章**。

现在判断「是不是合集」**只认「章 / 回 / 卷 / 集 / 部 / 篇 / 幕 / 折」这一级，不认「节」**（另外补了英文 `Chapter N` 的识别）：

| 文件内容 | 智能解析结果 |
|---|---|
| 第1章…第9章（合集） | 拆成 9 章 ✅ |
| 第10章（内含第一/二/三节） | **整篇一章** ✅ |
| 内部没标题、被按字数切成几段 | **整篇一章** ✅ |
| Chapter 1…Chapter 20 | 拆成 20 章 ✅ |

> 注意：文件**内部**还是一样的解析规则（「第X节」仍会被识别为章节标题），只有**智能解析的"要不要拆"这一步**改用严格判据。如果你确实想按「节」拆，选「一律解析文件内章节」即可。

**二、修「导入对话框底下的按钮不见了」**

`InkDialogShell` 这个对话框壳的内容区**不能滚动**，选项从 2 个变成 3 个之后，底部那行「取消 / 开始导入」被挤到屏幕外了。现在：

- 给壳加了**独立的按钮槽**（映射到对话框自己的按钮区，**永远可见**，不会被长内容挤走）；
- 内容区改为**超过 460dp 可滚动**，选项再多也够得到；
- 导入对话框、追加文件对话框都改成这个结构。

### v1.10.1（章节划分新增「智能解析」）

**问题**：一次选了两种文件 —— 一个 **1~9 章的合集**、一个**单独的第10章** —— 原来两个选项都不对：

- 「解析文件内章节」：第10章那个文件内部没有章节标题，解析器会**按 1.8 万字兜底切成好几段**；
- 「每个文件作为一章」：合集就变成**一整章**，里面塞了 9 章。

**现在新增第三个选项「智能解析（推荐）」，并且设为默认**：**逐个文件判断**，文件里确实是一章一章分好的就拆成多章，否则整篇作为一章（章名取文件名）。

> 上面那两件事合起来导 → 合集拆成 **1~9 章**，单独的 **第10章 整篇成为一章**，顺序也对（按章号插入）。

怎么判断「是不是真按章节排好的」？两个判据：

1. 各分片标题解析出的章号有**两个以上不同的值**（真章节几乎总是如此）→ 拆；
2. 分片标题里**没有「（2）（3）」这种兜底后缀**（按字数兜底切分才会加）→ 拆。

所以「合集」会拆开，而「第10章 xxx」即使内部没标题、被兜底切成几段，也不会被误拆成好几章。

**追加文件为章节**那里也换成了同样三个选项，默认同样是智能解析。

### v1.10.0（追加章节自动插到中间 + 章节自动排序）

**1. 追加文件为章节时，按章号插到正确位置**

以前往书里追加章节一律**扔到末尾**。现在如果追加的文件名带章号，会**插到对应位置**：

> 已有 `第1章`、`第3章`（中间缺第 2 章）→ 追加 `第2章 xxx.txt` → 结果自动变成 **1 → 2 → 3**。

- 只移动**新追加的章节**，已有章节之间的相对顺序**不动**（所以不会把整本重排一遍）；
- 一次追加多个、章号打乱的，也按章号从小到大依次插好；
- 解析不出章号的新章节保持追加在末尾，不会丢。

**2. 章节管理 ⋮ 新增「自动排序章节」**

给已经**打乱**的书用：一次把整本按章节标题里的「第N章」重排。规则：

| 情况 | 排到哪 |
|---|---|
| `序 / 序章 / 序言 / 自序 / 楔子 / 引子 / 前言 / 题记 / 引言 / Prologue / プロローグ…` | 第一章**之前** |
| `第X章 / 第X话 / 第X节 / 第X卷…`、`Chapter / Part / Book / Volume / Episode + 编号`（阿拉伯、全角、中文/日文汉字数字、罗马数字、英文数字单词都认） | 按编号**数字**升序（`Chapter 10` 在 `Chapter 2` 之后） |
| 解析不出章号的（含 `幕間 / Interlude` 这类位置不固定的） | **钉在原位**，既不前移也不后甩 |
| `后记 / 后序 / 尾声 / 终章 / 结语 / 番外 / 附录 / 外传 / Epilogue / あとがき…` | **最后** |

> 只动「能解析出章号」的章节：把它们按编号升序**填回原来占据的那几个位置**；认不出章号的原地不动。旧版把认不出章号的统一排到中后段，`幕間` 这类夹在正文章节之间的内容会被排错 —— 现在不会了。

- 点之前会弹确认框，把规则和章节数说明清楚；
- **章节里的标签、笔记会跟着章节一起移动**（底层重排时会同步改标记的章号），不会串位；
- 已经有序的书点它不会有任何变化（会先比较，顺序没变就不写库）。

### v1.9.4（多文件导入按文件名里的章号排序）

一次选很多个文件时（比如把一本书拆成 52 个「第N章 xxx.txt」），**系统文件选择器给的顺序往往是乱的**（甚至倒序）。现在导入前会先解析文件名里的章号并据此排序：

- 认这些写法：**`第52章`**、`第51回`、`第十二章`（中文数字也认，支持「二十三」「一百零五」）、`003 破境.txt`、`12、威胁.txt`、以及文件名本身就是一个数字；
- 解析出章号的**按章号升序排在前面**；解析不出来的**保持原相对顺序排在最后**（不会因为排序丢文件）；
- 章号相同时用文件名兜底比较，结果稳定、可复现；
- **合并为一本书**时，章节顺序就是排完的顺序，章节标题取自文件名（`第52章 取舍之间`）；
- **各自成为一本书**时也按同样顺序建书，于是书架上「最近导入」的排列也跟着有序。

> 例：乱序选入 `第52章…` `第25章…` `第50章…` `第28章…` `第51章…` `第32章…`，导入后章节顺序是 **25 → 28 → 32 → 50 → 51 → 52**。

### v1.6.0（删掉覆盖 / 仿真，点击边缘翻页带动画）

**删掉「覆盖」和「仿真」两种翻页动画**，只保留 **平移 / 无动画**。

原因是它们跟分页引擎打架：这两种效果的诉求是「**旧页压在新页上面**、跟着手指滑走」，而 `HorizontalPager` 的绘制顺序是**按页号递增**（页号大的盖住页号小的），靠改位移根本做不出来 —— 只能把旧页单独提到 pager 之上再画一层，于是状态变成两套（谁在上、方向、被揭开的是哪一页），还各自带出一串边界问题（两层同时画文字会「重叠」、缩放会让下页从两侧露出来、静止与拖动期间要切换画法……）。连着几版都在这个坑里打转，实测收益不值这个复杂度，**直接删掉**：需要「旧页在上」的效果就该换分页实现，而不是在 pager 上打补丁。

> 旧版本里存过 COVER / CURL 的设置**会自动回落到「平移」**（读取时遇到不认识的枚举名取默认值），不用手动改。

**点击屏幕最左 / 最右翻页，现在跟着翻页动画走。**

以前点击边缘是**硬切**（`scrollToPage`，一帧跳过去，没有任何过渡），手势拖动才有动画，两者观感不一致。现在：

- 点击左右边缘 → **带动画滑过去**（用与手势一致的翻页动画）；
- **音量键翻页**同样带动画；
- 跳转（目录、搜索结果、批注定位）和改排版重排后**仍然直接对齐**，不做动画 —— 那些场景要的是「立刻到位」。

选了「无动画」时，点击边缘和音量键也都是立刻切换。

### v1.5.3（修「新页好像压在旧页上面冒出来」—— 仿真去掉缩放）

**症状**：旧页确实在上层了，但**有时候新页会很快冒出来、看着像压在旧页上面**：往左翻时左边先冒出来，往右翻时右边先冒出来。

**根因**：我为了让「仿真」看起来像纸被掀起，给上层那页加了一个**以页面中心缩放**的效果（`scaleX/scaleY = 1 - 0.08×进度`）。页面一缩小，**它的左右两条边同时往里收**，于是下面那页从**两侧**都露出来了 —— 露出来的那侧正好是旧页本该盖住的那边，看起来就是「新页在旧页旁边冒出来、像在上面」。覆盖模式没有这个缩放，所以只有仿真会出现（这就是「有时候」的来源）。

**修法**：**仿真不再做任何几何变形**，纸感只用阴影表达（仿真 0.40，覆盖 0.22，都比之前更明显一点）。位移逻辑一个字没动。

**定位过程**（这次没猜）：`Log` 被这台机器的系统策略挡掉了（连 Error 级都没有），所以我做了个**带颜色标记的诊断版**（被揭开的那页染冷色、上层那页染暖色），用 `adb` 在慢速滑动过程中连拍截图，再用 Python 按列统计 R-B 色差，把每一帧里两页各自的位置量了出来：

- 覆盖 · 前翻：暖色 `0..1072 → 0..824 → 0..576`（旧页右边缘往左收），冷色从右侧长大 ✓
- 覆盖 · 后翻（干净的一次）：冷色从左侧 `72..216 → 72..464 → 72..712` 长大，暖色往右让开 ✓

两个方向、两种模式都对，唯独带缩放的仿真会让冷色铺满整屏 —— 与推测完全一致。另外把 `PagerState` 的源码掏出来核对了坐标约定：`currentScrollOffset = (currentPage + currentPageOffsetFraction) * pageSize`，正的 fraction 就是往后翻，我的位移公式和这个一致。

> 顺带说明：**「仿真」不是真正的卷页**，是「覆盖 + 更重的翻页阴影」。真卷页要对页面做曲面变形（canvas/shader），是另一个量级的工作。

### v1.5.2（重做覆盖 / 仿真 —— 旧页在上、往左滑走）

上一版把覆盖做反了：我让**新页压着旧页滑进来**，而正确的「覆盖」是**旧页压在新页上面、跟着手指往左滑走**，新页早就铺在底下等它揭开。仿真之所以还会「正文重叠」，根因也在这里：

**`HorizontalPager` 的绘制顺序是按页号递增的**（页号大的盖住页号小的）。上一版为了做「揭开」效果，把**新页**（页号更大）钉在视口里不动，结果它反而画在旧页**上面**，两页文字就叠在一起了。**靠改位移做不出「旧页在上」**——页号顺序是定的。

这一版改成**两层**：

- **下层**：所有页照常交给 pager，但拖动期间把「被揭开的那一页」的位移抵消掉，让它**钉在视口里**不动；
- **上层**：把「正在被翻走的那一页」单独提到 pager **之上**再画一层，跟着手指 1:1 移动，带自己的不透明底色。因为它是后画的，天然压在下面那页上面；
- 同时让下层里那份「正在翻走的页」**完全隐形**（`alpha=0`），避免同一页被画两份 —— 那样同样会看起来像文字重叠。

揭开方向由翻页方向决定：往右翻时旧页往左走、揭开的是下一页；往左翻时旧页往右走、揭开的是上一页。纸感：**覆盖**是一道轻阴影（0.22），**仿真**阴影更重（0.40）。**仿真不是真正的卷页仿真**（真卷页要用 canvas 做曲面变形），是「覆盖 + 翻页阴影」的近似 —— 早期版本给它加过一个「略微缩小」的形变，v1.5.3 已移除（原因见 v1.5.3 说明）。

拖动期间下拉打标签会暂时禁用（避免和翻页手势打架），松手后恢复。

### v1.4.2（三个行为开关 + 修「正文最后一行被截断一半」）

**修复：左右翻页时，页面最底下那一行字被竖向切掉一半。**

根因有两个，都在分页器里，而且互相叠加：

1. `continuation`（续排标记）**永远被设成 false**：分页器把段落切开跨到下一页时，没把「下一段开头是续排」标记出来。于是**渲染端**给每个跨页续排的段落片段都加了首行缩进（本来不该有）；
2. **分页器测量文本时用的是「不带首行缩进」的样式，渲染时却带缩进** —— 首行少放两个字，段落就可能多出一行，页面高度不够，最后一行溢出后被裁掉半截。

修法：修正续排标记；**首行缩进参与测量**（段落第一截带缩进量、续排那截不带）；行高取「名义行高」与「实测量一行的高度」中较大的那个，再留 1dp 余量。

| 音量键翻页 | 收起工具栏时音量下/上翻页；呼出工具栏时恢复调音量（v1.3.2 加的功能，设置里一直没入口，这次补上） |

### v1.2.1

**修复「导入文档 → 选好文件 → 按确定却什么反应都没，再试一次又好了」**。根因不在导入逻辑，而在系统文件选择器这一段，共四处加固：

1. **不再相信标准契约的解析结果**。原代码用 `ActivityResultContracts.OpenMultipleDocuments`，它在 `resultCode != RESULT_OK` 时**直接返回空列表**；而某些 ROM（实测 vivo 自带的文件管理器选择器）会在用户已经选好文件的情况下回一个非 OK 的 resultCode，于是 App 拿到空列表就**静默什么都不做**——表现出来就是「按了确定毫无反应」。现在改成自己发起 `ACTION_OPEN_DOCUMENT`，**不看 resultCode**，只要返回的 Intent 里有 Uri 就认（`clipData` / `data` / `EXTRA_STREAM` 三条路都试一遍）。
2. **选择器被系统回收后自动接上**。打开选择器时墨阅在后台，实测这台手机的系统会 `am_app_frozen`（fast_freezer）甚至 `am_kill ... single-cleaner` 把进程冻结/杀掉，此时选择器的结果就永远回不来了。现在发起选择器前会把「我要选文件了」同步落盘，结果一回来就清掉；如果重进 App 时发现这个标记还新鲜（5 分钟内），说明上一次被系统打断了，会**自动把选择器重新打开**并提示一句「上次的文件选择被系统回收了，已重新打开」。
3. **选好的文件立刻落盘**：万一进程在「选完文件、还没点开始导入」之间被回收，重进 App 会把「导入 N 个文件」设置框原样恢复出来，不用重新选、不用重新填。
4. **`file://` 也能读了**：部分 ROM 的选择器回的是 `file://` 而不是 `content://`，现在读取时两条路都会走（ContentResolver → 直接 File），并会尽力把授权持久化。

> **顺带一个手机侧建议**（能明显减少被冻结/清理，后台朗读也更稳）：
> 把墨阅加入白名单 —— 设置 → 电池 → 后台耗电管理 → 允许「后台高耗电」；
> i管家 → 应用管理 → 权限管理 → 自启动 → 允许。

- 导出完成后：文件写进**系统「下载」目录**（文件管理器里能找到），同时**弹出系统分享面板**，可以直接发微信、QQ 或传网盘。
- 内容干净：整本导出 = **书名 + 作者作为文件头**，之后每章一个标题加正文；单章导出 = 只有这一章的标题与正文。**绝不包含任何书签、高亮、笔记**。
- UTF-8 **带 BOM** + CRLF 换行，Windows 记事本、手机自带阅读器都不会乱码、不会错行。
- 大书**逐章流式写入**，不会一次性把整本书读进内存。详见下面「九、导出为 TXT」。

**4. 阅读器右上角三点改为直接进章节管理**（以前的入口是排版设置，现在排版设置仍在底栏「设置」里）。

**5. 章节管理页改成卡片列表**：每个章节一行卡片（序号徽标 + 标题 + 字数），右侧「⋮」菜单：阅读本章 / 导出本章为 TXT / 编辑正文 / 重命名 / 上移 / 下移 / 删除本章——比原来一排五个小图标清爽得多。

**6. 笔记与书签页可以直接删了**：每张批注卡片右下角多了一个删除图标（带二次确认）。之前这个页面只能看，删不掉。

### v1.1.0

1. **修复深色主题看不清字** —— 根因是正文样式没有显式指定字色，`BasicText` 在颜色未指定时会回退到 `LocalContentColor`，而这个回退值在深色主题下仍是深色，等于深底配深字。现在字色随主题显式下发，不再依赖回退。顺带把「深墨」「纯黑」两套主题的正文字色各提亮一档（`#DCD5C8 → #EAE3D6`、`#B9B4AC → #D6D1C8`），强调色也相应调亮，长时间阅读更省力。
2. **阅读器新增书籍详情页入口** —— 之前「设置 → 章节管理」点了只是退回书架，是个假入口。现在有两处真实入口：① 点顶栏的书名，直接进详情页；② 设置面板里的「章节管理」。
3. **追加文件也能解析章节** —— 之前往已有书籍（尤其是新建的手写书籍）里追加 TXT/docx，是一个文件硬塞成一章。现在追加时会先问你「章节划分」：**解析文件内章节**（自动识别「第X章」等标题，一个文件可拆成多章）或**每个文件作为一章**。书架导入的「合并为一本书」同样多了这个选项。
