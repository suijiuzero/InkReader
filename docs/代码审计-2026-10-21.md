## P1：正文和数据完整性

### 01. PDF 聚合新段落时漏掉新段首行

位置：[PdfParser.kt:118](../app/src/main/java/com/inkreader/parse/PdfParser.kt#L118)。验证：**提取生产聚合循环执行复现**。

`newPara && buf.isNotEmpty()` 分支保存旧段、清空缓冲区，但没有把当前 `line.text` 放入新缓冲区；当前行也不会在后续分支补入。段落间距变大，或上一行 `paraEnd=true` 时均可触发。四行样例“首段一 / 次段首行 / 次段末行 / 末段首行”最终只保留“首段一 / 次段末行”。丢失发生在导入正文阶段，用户看到的是成功导入的残缺内容。

建议：先判断并结束旧段，再统一追加当前行；同时用实际生成的多段 PDF 验证文本覆盖率，不能只检查成功返回章节。

### 02. 默认净网清洗会删除正常网址所在的整行

位置：[ChapterSplitter.kt:211](../app/src/main/java/com/inkreader/parse/ChapterSplitter.kt#L211)，默认开关见 `ShelfScreen.kt:1011`、`BookDetailScreen.kt:1021`。验证：**当前生产函数执行复现**。

只要含 URL 且整行不超过 72 字就返回水印，无需出现小说广告词。“参考资料：https://example.com”会整行消失。导入和整书重新分章默认开启清洗，技术资料、论文引用和含网址的对白都有误删风险；重分章成功后还会删除旧章节文件。

建议：正常链接默认保留；广告识别至少组合网址、广告措辞和独立行/装饰特征，低置信度只提示；净网修改应可预览或撤销。

### 03. 整书重分章的快照与提交之间，没有书籍写入互斥或版本检查

位置：[BookRepository.kt:904](../app/src/main/java/com/inkreader/data/repo/BookRepository.kt#L904)、[BookRepository.kt:995](../app/src/main/java/com/inkreader/data/repo/BookRepository.kt#L995)、`saveChapterText:1160`。验证：**静态确认操作顺序；未做并发设备复现**。

旧章节、批注和文件内容均在替换事务之前读取，解析/映射/写新文件也在事务外。期间同一本书若保存编辑、追加章节或新增批注，提交仍按旧快照执行 `DELETE chapters WHERE book_id=?` 并重建，随后删除旧文件。例如：重分章读取旧正文 → 用户离开忙碌页面后编辑保存新文字 → 重分章提交旧快照，新文字不再属于数据库里的任何章节。新增批注可能保留旧章号。

单次 SQLite 事务只能保护提交过程，不能验证快照仍是最新。详情页 `busy` 不是仓库级锁；取消页面协程也不能中断正在 IO 线程同步执行的切分和文件操作。

建议：所有同书写操作共享串行队列/Mutex，并建立内容版本；长计算后提交前校验版本，冲突则中止或重算。文件、样式、批注和章节替换按同一版本提交。

### 04. EPUB 缺页或损坏可以被静默当作成功导入

位置：[EpubParser.kt:61](../app/src/main/java/com/inkreader/parse/EpubParser.kt#L61)、[EpubParser.kt:122](../app/src/main/java/com/inkreader/parse/EpubParser.kt#L122)。验证：**静态确认**。

超过单条 8MB/累计预算的文本条目被跳过；ZIP 读取异常被 `runCatching` 吞掉并返回已经收集的部分内容；spine 指向的正文查不到时直接 return。只要还有一章可读，解析器就会返回成功，导入结果不说明缺失范围。`resolve:240` 还用表单式 URLDecoder 解码路径，把合法文件名 `chapter+1.xhtml` 中的加号变成空格，进一步触发静默缺页。

建议：必需 spine 资源读取失败应明确失败或报告“部分导入”及缺失条目；超限/CRC/解压错误不能静默丢弃；路径解码保留字面加号，按 URI 路径规则处理百分号转义。

## P2：算法、样式与交互正确性

### 05. 普通文件名的扩展名始终取不到

位置：[DocumentFormat.kt:142](../app/src/main/java/com/inkreader/parse/DocumentFormat.kt#L142)。验证：**当前生产函数执行复现**。

`name.substringAfterLast('/', "")` 在不含斜杠的 `notes.md` 上返回空串，导致扩展名丢失。仓库取得的显示名通常就是普通文件名。样例 `**bold**`、文件名 `notes.md` 返回 TXT，丢掉 Markdown 解析和样式；只有内容嗅探碰巧达到“两行标题/代码围栏”等阈值时才会命中 Markdown。

建议：无目录分隔符时保留完整文件名；覆盖普通名、路径名、大小写扩展名、未知扩展名和伪装容器。

### 06. 固定字数切分没有对超长单段执行硬拆分

位置：[ChapterSplitter.kt:840](../app/src/main/java/com/inkreader/parse/ChapterSplitter.kt#L840)。验证：**当前生产函数执行复现**。

循环先把整个段落放入缓冲区，超过阈值才 flush。设置 2000 字，输入 15 万字无换行正文，结果仍只有一个 15 万字章节。SMART 的字数兜底与单章 12 万字保护也复用此函数，因此这些保护不是真正上限。

建议：句末/段落边界优先，超长段落再按安全字符边界硬拆；输出必须有长度上界，不能拆开 UTF-16 代理对。用无换行、超长英文、emoji 和单段超过阈值的样例验证。

### 07. 字数兜底会直接粘连英文单词

位置：[ChapterSplitter.kt:269](../app/src/main/java/com/inkreader/parse/ChapterSplitter.kt#L269)。验证：**当前生产函数执行复现**。

四个以上空行分隔块时直接 `replace("\n", "")`；其余按行聚合的分支也直接 append。输入块内 `hello\nworld` 会变成 `helloworld`。不只是显示排版，落盘正文也被改变；无标题 TXT 的 SMART 兜底同样受影响。

建议：分章只决定源区间，不顺便改正文；如另设“合并断行”，需区分中西文、连字符和代码，且保留可逆映射。

### 08. 一个全书大标题压过所有真正章节标题

位置：[ChapterAssembler.kt:27](../app/src/main/java/com/inkreader/parse/ChapterAssembler.kt#L27)、[MarkdownParser.kt:51](../app/src/main/java/com/inkreader/parse/MarkdownParser.kt#L51)。验证：**两个当前生产入口均执行复现**。

固定取最浅标题级别。常见的“一个 H1 书名 + 多个 H2 章节”只生成一个全书章节；DOCX/HTML 经 ChapterAssembler、Markdown 自己的扫描均有此问题。不能假设最浅标题重复出现。

建议：区分单次文档标题、分卷标题和重复章标题；按层级频率、连续序号、正文分布选择章节层级，保留下一级标题结构。

### 09. 无空格标题仍被正文引用过滤器误杀

位置：[ChapterSplitter.kt:795](../app/src/main/java/com/inkreader/parse/ChapterSplitter.kt#L795)、`REFERENCE_CONNECTORS:832`。验证：**当前生产函数与 HTML 对照执行复现**。

章标记后紧接“对/和/的/是”等字符即拒绝。合法的“第二章对不起”被吞进上一章正文，三章样例只得到第一、第三章；HTML 相同样例识别出三章。单字符黑名单不能区分标题与句子引用。

建议：引用判断结合整个短语、标点、邻近标题序列与段落长度；不把一个常用汉字当充分拒绝条件，低置信度候选参与全局判断。

### 10. Markdown 围栏只记三个反引号，会把代码里的标题识别成章节

位置：[MarkdownParser.kt:88](../app/src/main/java/com/inkreader/parse/MarkdownParser.kt#L88)、`:145`、`:209`。验证：**当前生产解析器执行复现**。

`fenceOf` 把四个及更多反引号一律记为三个，`startsWith(fence)` 又允许过短的围栏关闭代码块。四反引号代码内出现三反引号后，下一行 `# 代码里的假标题` 会进入章节结果，真实代码结构被切坏；扫描标题层级和实际分章两处均受影响。

建议：记录围栏字符与开围栏长度，结束围栏必须足够长且尾部仅空白；扫描和切分共用相同的围栏状态机，减少重复规则。

### 11. 数字规则允许“万”，实际数字解析却不支持

位置：[ChapterSplitter.kt:1098](../app/src/main/java/com/inkreader/parse/ChapterSplitter.kt#L1098)。验证：**当前生产函数执行复现**。

候选规则允许“万”，`chineseToInt` 的单位表却只有十百千；“第一万章 测试”章号返回 null，排序和连续性判断失效。HTML 对“一万”能返回 10000，可借鉴分节计算，但必须补“万+十/百/千”、大写和溢出测试，不能只增加一个单位常量。

### 12. HTML 空元素 embed 会吞掉它后面的全部正文

位置：[HtmlTextExtractor.kt:165](../app/src/main/java/com/inkreader/parse/HtmlTextExtractor.kt#L165)。验证：**当前生产函数执行复现**。

`embed` 在跳过列表中，但仅以标签末尾 `/` 判断是否自闭合。普通 HTML `<embed src='a.pdf'>` 是空元素，没有 `</embed>`，提取器会一直等待结束标签。`<p>开头</p><embed ...><p>后续正文</p>` 仅返回“开头”。

建议：独立维护 HTML void 元素集合，不进入等待闭合状态；补带 `>` 的引号属性、script 文本等状态机边界样例。

### 13. 打开编辑器直接返回也会删除样式，拆章和合章同样丢样式

位置：[EditorScreen.kt:108](../app/src/main/java/com/inkreader/ui/editor/EditorScreen.kt#L108)、`:152`；[BookRepository.kt:1164](../app/src/main/java/com/inkreader/data/repo/BookRepository.kt#L1164)、`:739`、`:839`。验证：**静态确认完整调用链**。

退出不检查正文是否改变，persist 总会调用 saveChapterText，后者无条件删除 `.rich`。所以未修改正文就返回、或只改章名，也会抹掉粗体、代码、链接和块样式。拆章/合章使用新文件只写 text，再删除含原样式的旧文件，也没有迁移样式。

建议：未改正文时不重写正文；仅改名走元数据操作。真正编辑时迁移/明确降级样式；拆合对 RichBlock、Span、Link 做裁剪和平移，和正文同提交。

### 14. 正文编辑没有重定位既有批注和阅读锚点

位置：[BookRepository.kt:1160](../app/src/main/java/com/inkreader/data/repo/BookRepository.kt#L1160)。验证：**静态确认**。

保存只更新文件、字数和统计，没有调整 marks 或 lastCharOffset。在高亮之前插入十个字，原高亮仍在旧偏移；删除到批注之前则可能留下超出正文长度的区间。原批注 snippet 与实际高亮位置也会不一致。当前界面只提示保存，未告知批注失效。

建议：编辑保存使用文本变更区间映射，迁移批注和进度；完全删除的批注需保留说明或明确失效状态。不要以全书首次 snippet 命中替代锚点映射。

### 15. 追加章节的自动插入忽略分卷重编号保护

位置：[BookRepository.kt:672](../app/src/main/java/com/inkreader/data/repo/BookRepository.kt#L672)。验证：**静态确认**。

autoSortChapters 有 hasChapterNumberReset 保护，但 appendFilesAsChapters 最后无条件调用 insertByChapterOrder，后者全书按裸章号比较，也不看 volume。第一卷 1~10、第二卷 1~2，追加第二卷第 3 章，会插在第一卷第 4 章前。

建议：复用分卷感知排序，明确卷身份后仅卷内插入；卷归属不确定时保留追加物理顺序并提示，不自动跨卷移动。

### 16. 阅读进度异步写入可能被旧请求覆盖

位置：[ReaderSession.kt:815](../app/src/main/java/com/inkreader/ui/reader/ReaderSession.kt#L815)，交叉写入见 `TtsService.kt:479`。验证：**静态确认；未执行乱序调度设备测试**。

每次保存各自启动 IO 更新，没有串行写入或请求版本。快速翻页 A→B，A 的数据库操作若晚于 B 完成，最终恢复 A。阅读会话和 TTS 都能写同一个 book 进度，也没有约定由谁负责。切章读取已有代次保护，但落盘进度没有。

建议：按书保存最新进度、合并高频更新并串行提交；引入事件版本或单一进度拥有者，退出时刷完最后一次保存。

### 17. 滚动位置只记段首，长段落内阅读和搜索无法精确恢复

位置：[ReaderScreen.kt:1444](../app/src/main/java/com/inkreader/ui/reader/ReaderScreen.kt#L1444)、`:1487` 附近的跳转逻辑。验证：**静态确认**。

只观察 firstVisibleItemIndex，把位置存成 block.start，既不看段内像素位移，也不换算可见字符；跳转也只 scrollToItem。一个段落跨数屏时滚了几屏仍保存同一个偏移，搜索/笔记跳到长段落中间也只会来到段首。

建议：用段落稳定身份 + 段内可见字符位置保存锚点，借文字布局结果换算位置；像素偏移作为同排版下的辅助，字号变化仍以字符锚点重定位。

### 18. 当前章和上一章完整分页仍在主线程进行

位置：[ReaderSession.kt:360](../app/src/main/java/com/inkreader/ui/reader/ReaderSession.kt#L360)、`:424`、`:453`。验证：**静态确认执行上下文；未给出性能数值**。

全书页数统计迁到 Default，但 repaginate 同步执行；邻章 scope 使用阅读页 Main 协程，读取完成后也在 Main 运行完整上一章分页。大章/大字号下仍可能卡住交互；loadChapter 内 repaginate 与后续 loadNeighbors 还可能在首批预加载未完成时重复提交邻章任务。问题 06 会放大输入尺寸。

建议：准备不可变排版请求，把可安全后台执行的测量/分页移出 Main，发布时校验内容和排版代次；相同邻章/排版请求复用进行中的任务。实际耗时和线程安全需设备测量后确认。

### 19. 封面缓存无容量上限，也不随删书释放

位置：[CoverCache.kt:25](../app/src/main/java/com/inkreader/ui/component/CoverCache.kt#L25)，调用 `Common.kt:309`。验证：**静态确认**。

全局 HashMap 持有每一本加载过的 ImageBitmap，invalidate 只加版本，不移除缓存；删书也不通知缓存。默认 700×1000 的 ARGB 封面约需 2.8MB 像素内存，100 张量级约 280MB（估算，不是实测堆占用）。decodeFile 还在组合调用链执行，首次显示会同步解码。

建议：按像素字节限额的 LRU、按显示尺寸采样、后台解码；删书/清封面时驱逐对应键并清理封面文件。

### 20. 下一次导出会立即删除仍可能被读取的分享文件

位置：[BookExporter.kt:100](../app/src/main/java/com/inkreader/data/export/BookExporter.kt#L100)。验证：**静态确认**。

每次导出开始先删除 exports 目录所有文件；上次分享 Intent 交给接收应用后，接收方可能还未打开 URI。再次导出会让这个 URI 指向不存在的文件，同名导出也可能覆盖为另一本/新版本内容。

建议：每次导出唯一文件，按过期时间清理，不用“开始新导出”作为清除所有分享文件的条件。另需检查 API≤28 的同名公共下载文件直接覆盖失败时删除目标的行为，避免毁掉已有导出。

| 逐行诊断 | HTML 的 lineAnnotations/diagnostics 明确记录标题、分卷、引用拒绝、目录过滤、水印；Android 主要返回 Part 列表 | 优先借鉴数据结构，把拒绝原因和置信度带进导入预览 |
| 保守净网 | 相同正常参考 URL，Android 删除，HTML isWatermarkLine 返回 false | 借鉴“多个广告特征组合”方向，保留正常链接 |
| 引用判断 | “第二章对不起”样例：Android 两章，HTML 三章 | 借鉴结合短语而非单字的方向，加入双向反例后重写 |
| 中文数字“万” | Android null，HTML 一万→10000、一万零一十→10010 | 可移植单位分节思路，补边界/溢出/混合数词测试 |
| 分卷结构 | Android 已有卷名字段、卷归属提取和重编号检测 | 统一 Android 排序/追加的策略，无需再搬一套分卷内核 |
| 所谓同族投票/自学习 | 两端都是规则与短行签名统计，没有训练模型 | 用可解释的候选评分和测试集衡量，不以名称判断效果 |

**不建议直接搬 HTML 的完整解析器：**

1. `sliceChapters:3531` 从首个标题开始切，首章之前的前言没有出口；实际样例确认前言消失。
2. `filteredToc:3453` 附近没有把“目录过滤”限制在文首：两个正常短章节样例第一章被跳过，只剩第二章。
3. 固定字数按整行积累，15 万字无换行样例同样只得到一章，不能修复 Android 的超长段问题。
4. 章节英文序号用 parseInt：罗马/英文单词虽然正则允许，连续性校验却拿不到有效数字；Android 现有 romanToInt/englishToInt 更完整。
5. HTML 内的 `simulateOldV1_10_10` 是它自己写的旧版模拟，不等于当前 Android。不能用那个对比面板证明“新算法已经胜过当前项目”。

## 建议的算法升级形态

这轮最值得做的是 **源文本区间 + 可解释候选评分 + 分卷约束 + 可回滚应用**，不急着引入模型。

1. **先保证不丢原文。** 解析结果保留源段落/字符区间；标题提取、净网、断行合并分别记录变换。源区间是批注、链接、进度迁移的共同依据，减少后续 TextRemap 字符搜索猜测。固定字数切分必须有真正的输出长度上界。
2. **区分文档标题、分卷、章、小节。** 以重复程度、序号连贯性、章节跨度、样式层级共同选章级，单独处理只有一次的书名 H1。编号允许缺章、插章、番外和卷内重置；不按全书裸数字强行重排。
3. **候选先评分，再在全局序列里取舍。** 候选携带来源规则、标题形态、上下文、数字/卷身份、拒绝原因；正文引用和弱数字列表降低得分，而非一个字一票否决。对不确定文档可显示两个分章方案。
4. **所有提交都可审阅和失败恢复。** 预览报告新增/合并章节、删除行数、批注受影响数及不确定项；正文、样式和批注绑定版本。长计算的快照冲突必须被识别，成功前不销毁旧版本。
5. **用真实语料评估。** 建议先收集 30~50 份可合法使用且人工标过章节边界的小语料：中文小说、英文、日文、短章、分卷重编号、目录、技术资料、不同 Markdown 围栏、DOCX 层级、实际 EPUB/PDF。合成样例继续保留，但不让它代替真实文档。

建议评价指标：章节边界准确率/召回率、正文保留率、正常行误清洗率、批注/链接映射成功率、最坏单章长度、导入/重分章耗时与峰值内存。**没有基准数据前，不宣称识别率或自学习提升百分比。**

## 额外的资源与测试缺口

- 20,000,000 字符的重分章上限不是内存预算。TextRemap 的原位置数组约 80MB、输出逐字映射总量又约 80MB，尚未计原文、规范化、切分副本和样式；建议改区间映射、分阶段处理及预算限制。本轮没有做手机 OOM 压测。
- ZIP 的保留数据上限没有约束全部实际解压工作。跳过 DOCX/EPUB 条目后 closeEntry 仍会耗时读完；FormatDetector.inspectZip 也有同类情况。需总解压字节/条目/耗时预算，并可取消，不能只限制“最后存了多少文本”。
- 导入预览每次选项变化重新读取并完整解析最多五个文件，没有防抖或解析缓存；TXT 默认清洗路径又先执行默认解析再重新解码切分。建议按文件和选项版本缓存中间表示，取消旧任务时在循环中响应取消。
- 当前 47 项正式测试主要覆盖章节规则、编码、批注平移和 TextRemap，无法发现 PDF 聚合、真实仓库并发、无编辑丢样式、滚动段内恢复或分享接收时机问题。应把上述复现整理为正式回归，并补隔离数据库/临时目录的 Android 集成测试；不要直接使用用户书库测试故障路径。
- 当前 clear/delete 路径仍有吞异常和孤儿资源清理问题，部分 UI/应用级 scope 没有统一错误出口，建议专项补故障注入。此处不把所有理论 IO 异常逐个计入 20 项。

## 推荐修复顺序

1. 正文安全：01 PDF、02 水印、04 EPUB，以及 03 同书写操作互斥/版本。
2. 格式与数据：05 扩展名、13 样式保存、14 编辑批注、15 分卷追加。
3. 算法：06/07 固定字数与正文保留、08 层级、09 引用判断、10 围栏、11 数字、12 HTML 空元素。
4. 阅读与资源：16/17 位置保存、18 分页调度、19 封面预算、20 分享生命周期；用真机测量上述内存与耗时预算。

保留当前可用的书籍与备份，先做可复现缺陷修复和基准测试，再扩大算法调整范围。
